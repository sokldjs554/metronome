# 설계

## 한 문장

배포된 시계열 예측 모델을 **언제 다시 학습할지**를, 정책과 무관하게 한 번만 학습한 "재학습 캐시" 위에서
비교하고, 그 결론을 그대로 실행하는 서비스(감시 → 재학습 → 검증 → 무중단 교체)를 붙였다.

## 왜 이 문제인가

Model Craft 같은 플랫폼은 모델을 학습하고 비교해 REST API 로 배포한다. 배포 직후가 아니라 **그 다음**이
운영의 대부분이다: 데이터는 계속 바뀌고, 모델은 조용히 낡는다. 매일 재학습하면 안전하지만 비용이 들고,
재학습을 안 하면 싸지만 오차가 자란다. 둘 사이 어딘가에 "오차를 보고 필요할 때만" 이 있다. 이 프로젝트는
그 세 선택을 같은 데이터·같은 모델·같은 척도로 비교하고, 그 결과대로 움직이는 파이프라인을 만든다.

## 핵심 설계 결정

| 결정 | 이유 | 대안과 버린 이유 |
|---|---|---|
| **재학습 캐시** — 스트림의 매일 콜드 학습 모델을 한 번만 만든다 | 콜드 재학습은 정책과 무관하므로, 수십 개 정책을 학습 없이 비교할 수 있다 (365회 학습으로 20개 정책) | 정책마다 재학습: 20배 비용. 웜 스타트는 순차 의존이라 별도 실행 |
| **고정 평가 척도** — 초기 학습 구간의 통계로 모든 정책을 평가 | 재학습이 스케일러를 바꿔도 비교가 흔들리지 않는다 | 재학습별 척도: 정책 간 MAE 가 비교 불가 |
| **배포 지연 하루** — d일 재학습 모델은 d+1일부터 서빙 | 야간 학습·아침 배포라는 보수적 가정. 정책의 이득을 과장하지 않는다 | 즉시 적용: 작은 모델에서는 가능하지만 일반화하기 어렵다 |
| **해결된 오차만 감시** — 96시간 지평이 끝난 예측만 통계에 넣는다 | 실제 서비스가 알 수 있는 정보만 쓴다 (미래 누출 없음) | 부분 지평 사용: 빠르지만 편향 |
| **검출기 코드 공유** — 시뮬레이션과 서비스가 같은 `metronome.drift` 를 쓴다 | 오프라인에서 고른 정책이 온라인에서 그대로 동작한다 | 서비스용 재구현: 두 결과가 다를 때 원인을 못 찾는다 |
| **fail-closed 레지스트리** | 잘못된 ONNX 가 서비스에 오를 수 없다 ([ADR 0001](adr/0001-fail-closed-registry.md)) | 신뢰하고 로드: 조용한 오답 |
| **서빙 이미지에 torch 없음** | 작은 이미지, 좁은 공격면, 학습 코드와 서빙 코드의 경계가 명확 | 단일 이미지: 간단하지만 수백 MB 와 학습 의존성을 서빙에 끌고 간다 |
| **숫자 마커** — 문서의 모든 수치가 JSON 을 가리킨다 | 결과를 다시 만들면 문서가 틀린 곳에서 CI 가 멈춘다 | 손으로 옮기기: 늘 어딘가 하나가 다르다 |

## 코드 지도

| 경로 | 역할 |
|---|---|
| `metronome/data` | 소스 고정, 다운로드·검증, 스키마 검사, Polars 전처리, 스케일러·윈도, 분할 |
| `metronome/models` | naive · seasonal naive · Linear · NLinear · DLinear · PatchTST |
| `metronome/train` | 단일 학습 루프 (시드, 조기 종료, lr 스케줄, 웜 스타트) |
| `metronome/eval` | 지표, 블록 부트스트랩, LTSF 표준 프로토콜 러너 |
| `metronome/cadence` | 재학습 캐시(병렬), 정책 시뮬레이션, 비교 |
| `metronome/drift` | RatioRule · Page–Hinkley · ADWIN |
| `metronome/export` | ONNX 내보내기 · parity · INT8 · 벤치 |
| `metronome/serving` | 레지스트리, 엔진, 모델 교체, 감시, 리플레이, FastAPI, worker, 초기 배포 |
| `metronome/tracking` | MLflow 미러 |
| `metronome/bigdata` | Polars / pandas / PySpark 대용량 단계, Spark standalone 클러스터 실행(`cluster.py`) |
| `metronome/report` | 요약 JSON, SVG 차트, 대시보드 근거 파일 |
| `metronome/cli.py` | 모든 단계의 명령 |

## 범위

- 학습·서빙은 컨테이너 묶음 하나(api + worker + 공유 레지스트리) 단위이고, Kubernetes 매니페스트는 CI 의 kind 클러스터에서 검증한다. 모델 검증은 해시와 참조 입출력, 접근 제어는 API 키 하나다
- 데이터는 공개 벤치마크이고, 재학습 비용은 측정한 CPU 초와 재학습 횟수로 센다
- 재학습 정책 비교는 모델 효과와 섞지 않기 위해 DLinear 로 고정했고, 모델 구조는 사전 등록한 Optuna 탐색(H5)과 계열 리더보드에서 따로 본다
