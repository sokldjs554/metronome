# ADR 0001 — 파일 레지스트리와 fail-closed 모델 교체

날짜: 2026-10-06 · 상태: 채택

## 맥락

서비스는 멈추지 않아야 하고(non-stop), 재학습은 자주 일어난다. 교체 과정에서 생길 수 있는 사고는 세 가지다.

1. 내보낸 ONNX 파일이 학습한 PyTorch 모델과 다른 함수를 계산한다(내보내기 버그, 연산자 미지원).
2. 디스크의 파일이 등록 시점과 다르다(덮어쓰기, 부분 복사, 변조).
3. 교체 순간에 요청이 실패하거나, 서로 다른 모델이 반쯤 섞여 응답한다.

## 결정

- **레지스트리는 디렉터리다.** `versions/<v>/model.onnx` + `reference.npz` + `manifest.json`, 활성 버전은 `ACTIVE` 파일.
  MLflow 는 이를 거울처럼 기록하지만, 서비스가 읽는 진실은 디렉터리다. 외부 서비스가 죽어도 서빙은 계속된다.
- **참조 입출력 쌍을 모델과 함께 저장한다.** 내보낼 때 실제 학습 창에서 뽑은 입력 두 개와 PyTorch 출력을 기록한다.
  활성화 전에 ONNX Runtime 으로 같은 입력을 돌려 최대 절대 편차가 1e-4 이내인지 확인한다.
- **해시를 다시 계산한다.** `model.onnx`, `reference.npz` 의 SHA-256 이 manifest 와 다르면 활성화를 거절한다.
- **거절은 조용하지 않다.** `activate` 는 422 와 이유를 돌려주고, 기존 모델이 계속 서빙한다. `/ready` 는 검증을
  통과한 모델이 메모리에 있을 때만 200 이다.
- **교체는 포인터 교체다.** 요청 처리는 시작 시점에 모델 참조를 잡고 끝까지 그 참조를 쓴다. 교체는 속성 대입
  한 번이며 잠금은 교체 순서를 정할 때만 쓴다. 테스트 `test_hot_swap_never_drops_a_request` 가 이를 고정한다.
- **학습 코드는 서빙 이미지에 없다.** 서빙 이미지는 ONNX Runtime 과 NumPy 만 설치한다. 재학습은 별도 worker
  (PyTorch)가 하고 API 에 활성화를 요청한다. 데모 이미지만 둘을 한 프로세스에 둔다.

## 결과

- 좋은 점: 잘못된 파일이 서비스에 올라갈 수 없고, 교체가 요청을 깨지 않으며, 서빙 이미지가 작다.
- 비용: 참조 쌍을 만들고 검증하는 데 수백 ms 가 든다. 버전마다 ONNX 파일을 복사한다(DLinear 262KB).
- 하지 않는 것: 다중 노드 간 레지스트리 동기화, 롤백 자동화(수동 `activate` 로 가능), 인증서 기반 서명.
